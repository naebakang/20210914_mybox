## 작업 컨벤션

- 기존 폴더 구조는 어디에 새 파일/폴더를 둘지 먼저 물어보지 않고는 바꾸지 않는다.
- 그 외의 경우, 되돌릴 수 있는 로컬 작업(설치, 빌드, 스크립트 실행, 현재 작업에서 명백히
  필요한 파일 생성 등)은 기본적으로 확인 없이 진행한다.
- 한 가지 예외: `git config`는 절대 실행하지 않는다 — git identity 설정은 사용자가 직접 하도록
  요청한다.
- 한국어로 응답한다. 단, 커맨드/코드/고유명사는 원문(예: 영어) 형태 그대로 유지한다.
- 이 세션에서 사용자가 입력하는 모든 프롬프트는 `.claude/settings.json`에 설정된
  `UserPromptSubmit` 훅을 통해 `log_command.log`(프로젝트 루트, gitignore 대상 — 소스가 아닌
  로컬 런타임 데이터)에 한 줄씩 `<timestamp>\t<prompt text>` 형식으로 기록된다.
- 루프를 표현식 하나로 압축하는 문법(list/set/dict comprehension, generator expression,
  `map`/`filter`/`lambda`)은 피한다. comprehension이 더 짧더라도, 명시적인 `for` 루프(이름 붙인
  누산 변수를 두고 루프 본문에서 `.append`/`.add`/`.update` 호출)로 풀어서 작성한다. 사용자는
  인라인 comprehension을 한눈에 읽기 어려워하며, 루프를 풀어 쓰는 쪽을 선호한다.

## 이 프로젝트가 하는 일

Google Form 자동 회신 서비스. 하나 이상의 Google Form을 폴링해서 새 응답을 찾고, 설정된 문항
제목으로부터 응답자의 이메일(과 전화번호)을 추출하고, 이메일 형식을 검증한 뒤, 폼별 메일
템플릿을 사용해 Gmail API로 알림을 보낸다. 무인 운영이 가능하도록 장시간 구동되는 루프(기본:
300초마다)로 동작하며, `restart: unless-stopped`로 설정된 Docker 컨테이너로 패키징된다.

- **인증**: 단일 Workspace 서비스 계정(키는 `configs/*.json`에 위치, gitignore 대상 — 절대
  커밋하지 말 것)이 도메인 전체 위임(domain-wide delegation, `admin@sumokhoe.co.kr` Workspace
  관리자 콘솔에서 승인됨)을 통해 `biz@sumokhoe.co.kr`을 임퍼스네이션(impersonate)해서 Forms API
  (`forms.responses.readonly`, `forms.body.readonly`)와 Gmail API(`gmail.send`)를 호출한다.
  `src/app/object/google_api_client.py`가 이걸 담당한다: `GoogleAPI`는 공유 static 헬퍼
  `_build_credentials(path_service_account_json, subject_email, scopes)` 하나만 갖는 기반
  클래스이고, `Forms`와 `Gmail`이 각각 이를 상속해서 자기 자신의(더 좁은) `SCOPES` 클래스
  속성으로 credential을 만들고, 해당하는 `googleapiclient.discovery.build(...)` 클라이언트를
  감싼다 — `Forms.get_form(form_id)` / `Forms.list_responses(form_id)`(페이지네이션은 내부에서
  처리, 원본 응답 dict의 평탄한 리스트를 반환)와 `Gmail.send_mail(to_email, subject, body,
  from_email)`(MIME 메시지를 만들고 base64 인코딩). 각 서브클래스는 하나의 합쳐진 scope
  credential을 공유하는 대신, 자기만의(최소 권한) credential 객체를 따로 가진다.
- **핵심 모듈**: 책임(구글 API 접근 vs. 폼별 개체 vs. 오케스트레이션)에 따라 파일 세 개로
  분리돼 있다 — `src/app/object/google_api_client.py`(`GoogleAPI`/`Forms`/`Gmail`, 위 인증
  항목 참고), `src/app/object/form_target.py`에 `_FormTarget`(폼마다 하나씩: 폼 ID,
  이메일/전화번호용 문항 제목, 상태 파일, 메일 템플릿 디렉토리 — 순수 상태 + CSV/mailed-email
  로드·저장만 담당, API 호출 없음)이 있고, `src/app/procedure/auto_reply_orchestrator.py`에
  `GoogleFormAutoReply`(더 이상 파일시스템을 직접 건드리거나 자기 API 클라이언트를 스스로
  만들지 않는다 — 생성자가 `ins_set_project`(`SetProjectLive`, `forms:` 리스트와 credential
  이외의 설정을 읽는 데 씀)와, 이미 만들어진 `ins_forms_client`/`ins_gmail_client`를 받는다.
  전부 `src/app/container.py`가 wiring한다 — 아래 "엔트리 포인트 / DI wiring" 참고)가 있다.
  `check_once()`는 모든 폼 타깃을 순회하며
  각각 한 번의 폴/검증/발송 사이클을 수행한다(한 폼에서 실패해도 로그만 남기고 다른 폼에는
  영향을 주지 않음). `GoogleFormAutoReply` 자체에는 더 이상 `while` 루프가 없다 — `run_cycle()`이
  딱 한 번의 패스(`check_once()`로 폴링, 그리고 간격이 됐을 때 도메인 리포트와 재발송-재시도
  패스도 — 아래 해당 항목 참고)를 수행하고 리턴한다. `src/app/procedure/cycle.py`의 `Cycle`이
  이걸 무한히 반복시키는 쪽이다(아래 "엔트리 포인트 / DI wiring" 참고). 각 폼의 처리된 응답은 자체
  CSV 상태 파일(`index, response_id, create_at, answer_email, answer_phone, mail_send_success,
  mail_resend_success, mail_third_send_success, answer_fix_email, time_first_send_attempt`)에
  `mail_template_dir` 안에서 추적되므로, 재시작해도 재발송되지 않는다. `create_at`은 응답이
  실제로 제출된 시각으로, Forms API 응답 객체의 `createTime` 필드를 그대로 가져온 것이다
  (그 필드가 없으면 `'nan'`) — first-run/중복/발송 결과와 무관하게 새 응답마다 항상 기록된다,
  아래의 `time_first_send_attempt`와 다르게. 주간 응답 추이 리포트를 계획하다가 이 CSV 어디에도
  응답이 실제로 언제 제출됐는지 기록이 없다는 걸 발견해서 추가했다.
  `answer_fix_email`은
  기본값이 `'nan'`이며 오직 `__resend_with_domain_fix`(아래 재발송 재시도 항목 참고)에서만
  설정된다 — 발송 성공/실패 여부와 무관하게, 그 시도에 사용된 보정 주소가 기록된다(어느
  쪽이든 그 주소로 fix-and-resend 시도가 있었기 때문).
  **첫 실행 안전장치**: 프로세스가 시작될 때 어떤 폼의 상태 파일이 아직 존재하지 않으면
  (`_FormTarget.is_first_run`), 그 첫 배치의 응답들은 `__send_mail`을 호출하지 않고 CSV에만
  기록된다 — 이후 폴링 사이클에서 발견되는 응답만 실제로 메일이 발송된다. 이 장치가 존재하는
  이유는, 2026-07-15에 garmin/nutrition 상태 파일을 새 경로로 옮겼을 때 과거의 응답 이력
  전체가 "새 응답"으로 보여 대량 발송된 사고(잡히기 전까지 실제 이메일 151통 발송) 때문이다.
  완전히 새로운 폼이나, 상태 파일 경로/포맷이 다시 바뀌는 어떤 폼이든 이 안전장치에 의존해서
  같은 사고를 반복하지 않는다 — 왜 있는지 이해하지 못한 채로 제거하거나 우회하지 말 것. 각
  응답 행은 `mail_send_success`도 기록한다: 실제로 발송이 시도됐다면 `True`/`False`(중복으로
  스킵된 행도 `False`로 기록됨 — 아래 dedup 항목 참고), 첫 실행에 시딩된 행처럼 발송 자체가
  스킵된 경우에는 문자열 `'nan'`(실제 true/false 결과가 아님). `time_first_send_attempt`는 그
  첫 시도의 ISO8601 UTC 타임스탬프 문자열이다(예: `'2026-08-19T09:39:32.397512Z'`, Forms API
  자체의 `createTime` 스타일과 동일 — 첫 실행에 시딩된 행과 중복으로 스킵된 행 모두 `'nan'` — 어느
  쪽도 실제 시도가 없었기 때문). `GoogleFormAutoReply.__now_iso()`가 생성하고, 재발송 대기 시간
  판단(아래 재발송 재시도 항목)에 쓰이는 `__seconds_since()`가 이 값을 소비한다 — `__seconds_since()`는
  먼저 ISO8601로 파싱을 시도하고, 실패하면 옛 epoch 초 문자열로 간주하는 폴백을 타므로, 이 형식
  전환(2026-08-19) 이전에 쓰인 행도 강제 마이그레이션 없이 계속 동작한다. 다만 운영 중인 두 파일
  (`data/mail_template/20260715_{garmin,nutrition}/processed_response_id.csv`)은 일관성을 위해
  그 시점에 `build_up/`의 일회성 스크립트로 실제 값도 함께 마이그레이션했다.
- **제출 간 동일 이메일 dedup**: 새 응답 감지(`__get_new_responses`)는 오직 구글이 부여하는
  `response['responseId']`로만 dedup을 한다 — 응답 이메일이라는 개념이 없어서, 같은 사람이
  같은 이메일로(전화번호 등 다른 답변이 다르더라도) 폼을 두 번 제출하면 서로 다른 response
  ID 두 개, 별개의 메일 발송 두 번이 생겨버린다. `_FormTarget.set_mailed_email`이 이 틈을
  메운다: 해당 폼에서 "이미 알려진" 것으로 간주되는 모든 주소를 소문자로 모은 집합이며,
  실제 발송(`add_processed_record`, `mail_send_success`가 `True`일 때), 첫 실행 시딩 행
  (`add_processed_record`, `mail_send_success`가 문자열 `'nan'`일 때 — 의도적인 선택: 한 번도
  메일이 발송된 적 없는 과거 이력 배치에서 본 주소라도 "알려진" 것으로 취급해서, 이후 재제출
  때도 메일이 나가지 않게 함), 단순 재발송(`__resend_plain`), 도메인 보정 재발송
  (`__resend_with_domain_fix` — 원본 주소와 보정된 주소를 둘 다 추가한다. CSV에는 원본 주소만
  영구히 남기 때문)으로부터 채워진다. `__process_form_once`에서, 첫 실행이 아닌 새 응답의
  이메일이 유효하고 이미 이 집합에 있으면, 그 응답은 `mail_send_success=False`,
  `time_first_send_attempt='nan'`으로 기록되고 `__send_mail`은 호출되지 않는다. 실제 발송
  실패와 같은 `False` 값을 재사용하는 것은 의도적이다(어떻게 안전하게 유지되는지는 아래
  참고) — 별도의 sentinel 값을 쓰지 않는다. 비교는 대소문자를 구분하지 않는다.
  영속화: 각 폼의 집합은 `_FormTarget.save_mailed_email()`을 통해 자체
  `mail_template_dir/mailed_email.txt`(평문 텍스트, 한 줄에 소문자 주소 하나씩 — 가장 단순한
  읽기/쓰기 경로를 위한 선택이며 `unique_email_domains.txt`와 같은 컨벤션)에 기록되며,
  `__process_form_once`에서 처리된 응답마다, 그리고 `__resend_failed_mail`의 상태 변경이
  있었던 매 패스마다 호출된다. 이 파일이 존재하는 순간부터는 이 파일이 source of truth가
  된다. `_FormTarget.__init__`은 이 파일이 아직 존재하지 않는 최초 한 번에 한해서만 CSV
  이력(`mail_send_success`가 `True` 또는 `'nan'`인 행, 혹은 `mail_resend_success`/
  `mail_third_send_success`가 `True`인 행)으로부터 집합을 재구성하는 폴백을 탄다 — 그래서
  이 기능으로 업그레이드해도 이미 발송됐던(또는 이미 시딩됐던) 대상을 잊어버리지 않는다.
  `processed_response_id.csv`와 마찬가지로 이 파일도 실제 응답자 이메일(PII)을 담고 있어서
  gitignore 대상이며 추적되지 않는다.
  **중복 처리에 `False`를 재사용해도 안전한 이유**: `__resend_failed_mail`은
  `time_first_send_attempt`가 `'nan'`이 아닌 행에만 동작한다 — 중복으로 스킵된 행은 항상
  `'nan'`을 유지하므로(실제 시도가 없었기 때문에), `mail_send_success`가 실제 실패와
  똑같이 `False`로 보이더라도 재발송-재시도 스캔에 절대 걸리지 않는다. 도메인 리포트도
  별도로 `mail_send_success`가 `True`인 행만 카운트하므로, 중복 스킵 행은 실패 행과
  마찬가지로 거기서도 제외된다. CSV의 `answer_fix_email` 컬럼은 이전까지 알려져 있던
  한계 하나를 해소한다: 프로세스 재시작을 거쳤을 때, `__resend_with_domain_fix`로만
  성공한 행은 예전에는 `mailed_email.txt`가 어쩌다 유실될 경우 CSV의 원본(오타난)
  `answer_email`로만 복원 가능했다 — 실제로 메일을 받은 보정된 주소는 그 영속 파일을
  통해서만 살아남는다는 보장밖에 없었다. 이제는 `_FormTarget`의 CSV 재구성 폴백도
  `mail_third_send_success`가 `True`인 경우 `answer_fix_email`로부터 보정된 주소를
  시딩하므로, `mailed_email.txt` 없이도 살아남는다.
- **재발송 재시도(최대 총 3회 발송 시도)**: `mail_resend_interval_sec`(기본 600초,
  `run_cycle()`에서 호출되는 `GoogleFormAutoReply.__resend_failed_mail`)마다, 프로세스는 모든 폼의
  메모리 내 처리 기록 리스트를 스캔해서 `mail_send_success`가 `False`이고,
  `mail_resend_success`가 아직 `'nan'`이며, `time_first_send_attempt` 이후
  `mail_resend_wait_sec`(기본 6시간) 이상 지난 행을 찾는다. "이 주소가 존재하지 않는다"를
  "다른 어떤 에러다"와 구분해줄 신호가 없다 — Gmail API의 `send()`는 명백히 형식이 잘못된
  게 아니면 뭐든 받아들이고, 실제 전송 실패는 나중에 발신자의 메일함으로 오는 비동기
  bounce로만 알 수 있는데 여기서는 그걸 읽지 않는다 — 그래서 6시간 대기 + 단순 재시도가
  일시적 실패와 오타난 도메인을 구분하는 저비용 근사치 역할을 한다.
  대상이 되는 각 행에 대해:
  1. `__resend_plain`이 원본 `answer_email`을 변경 없이 그대로 재시도한다. 결과는
     `mail_resend_success`에 들어간다. 이게 성공하면 그 행은 끝 — 더 이상 시도하지 않는다.
  2. 1단계가 실패했을 때만, `__resend_with_domain_fix`가 `answer_email`의 도메인을 보정해서
     한 번 더 발송한다. 두 가지 경우가 있다:
     - `answer_email`에 `'@'`가 있는 경우: `'@'` 뒤 부분을 오타난 도메인으로 보고, 알려진
       모든 도메인 중 가장 가까운 것을 찾아서(`difflib.get_close_matches`, `cutoff=0.0` —
       `path_email_domain_report`로부터 온 알려진 도메인 목록이 비어있지 않다면 품질이
       나쁘더라도 항상 뭔가 하나를 반환함) 그 보정된 도메인으로 주소를 다시 만든다.
     - `answer_email`에 `'@'`가 전혀 없는 경우: `__find_domain_substring`이 알려진 도메인
       목록을 스캔해서 `answer_email` 안에 리터럴 부분 문자열로 나타나는 도메인을 찾는다
       (대소문자 구분 없음, 겹칠 경우 더 긴 매치가 우선). 찾으면 그 부분 문자열 앞부분이
       local part가 되고 주소는 `local_part@matched_domain`으로 재구성된다. 문자열 안에
       알려진 도메인이 하나도 없으면 그 행은 스킵된다(`mail_third_send_success=False`,
       `answer_fix_email`은 `'nan'`을 유지) — 알려진 도메인 목록이 비어있을 때와 동일하다.
     어느 경우든, 재구성된 주소는 `answer_fix_email`에 기록되고 발송된다. 결과는
     `mail_third_send_success`에 들어간다. 결과와 무관하게 이게 마지막 시도다 — 이후로는
     그 행을 다시 재시도하지 않는다. 이 단계 자체가 스킵될 때(알려진 도메인이 아직
     없거나, 알려진 도메인 부분 문자열 매치가 없거나, 보정된 주소가 여전히
     `EMAIL_REGEX`를 통과하지 못할 때)는 `answer_fix_email`이 `'nan'`을 유지한다.
  두 단계를 합치면 단순 재시도 실패를 "아마 일시적 에러는 아니다"로 판단하게 되지만,
  도메인 보정 자체는 여전히 "실패 원인이 local part가 아니라 오타난 도메인일 것"이라고
  가정하며, 이미 멀쩡하지만 아직 `path_email_domain_report`에 알려지지 않은 도메인을
  가장 가까운 알려진 도메인으로 "보정"해버릴 수도 있다.
- **이메일 도메인 리포트**: `email_domain_report_interval_sec`(기본 11시간, `run_cycle()`에서
  호출되는 `GoogleFormAutoReply.__write_email_domain_report`)마다, 프로세스는 모든 폼의
  메모리 내 처리 기록 리스트를 스캔해서 `mail_send_success`가 `True`인 행(실제 발송분만 —
  첫 실행 시딩분, 중복 스킵분, 실패/스킵분은 제외)의 `answer_email` 도메인을 모으고,
  중복 제거·정렬된 목록을 `path_email_domain_report`(`data/mail_template/unique_email_domains.txt`)에
  한 줄에 도메인 하나씩 다시 쓴다. 프로세스 시작 직후 한 번 즉시 실행되고, 이후로는 매
  간격마다 실행된다. 타이머는 메모리에만 있으며 재시작하면 리셋된다.
- **설정**: `configs/set_project.yaml`의 `google_form_auto_reply:` 키 아래. 최상위에는 공유
  설정(서비스 계정 경로, 발신 이메일, 폴링 간격, 이메일 도메인 리포트 경로/간격, 메일
  재발송 스캔 간격/대기 시간)이 있고, `forms:`는 폼마다 하나씩(`key`, `form_id`,
  `question_title_email`, `question_title_phone`, `path_state_file`, `mail_template_dir`)
  들어있는 리스트다. 문항 제목은 실제 폼에 표시되는 정확한 한국어 텍스트다(예:
  `'이메일 주소'`, `'전화번호(ex.01012345678)'`) — 고정된 영어 라벨이 아니다. 현재 설정된
  폼: `garmin`, `nutrition`. 각각 `data/mail_template/<dir>/` 아래에 자기 폴더를 가지며
  `subject.txt`, `body.txt`(평문 텍스트, Gmail 메시지로 그대로 읽힘), `processed_response_id.csv`
  (런타임 상태, PII — 아래 Git 섹션 참고, `mail_template/`의 나머지가 추적되는 것과 달리 이
  파일만 별도로 gitignore됨)를 담고 있다. `configs/env.py`는 부차적인/레거시 설정 표면이다
  (이 기능보다 먼저 있었고, 대부분 이 기능에서는 쓰이지 않는다).
- **엔트리 포인트 / DI wiring**: `main.py`는 `src/app/container.py`의 `bootstrap().run()`을
  호출한다. `Container`(`dependency_injector.containers.DeclarativeContainer`)가 실제 의존
  관계를 선언하며, 그 뿌리는 `src/app/object/set_project_live.py`의 `SetProjectLive`다
  (`path_file`을 들고 있고, `get_config()`는 마지막으로 읽은 이후 파일의 mtime이 갱신됐을
  때만 YAML을 다시 읽고 다시 파싱한다 — 한 번만 로드하는 게 아니라 스스로 최신 상태를
  유지하는, 설정의 단일 진실 공급원이다): `pro_set_project`는
  `providers.Singleton(SetProjectLive, path_file=...)`이고, `pro_forms_client` /
  `pro_gmail_client`는 각각 `providers.Singleton(Forms/Gmail, path_service_account_json=...,
  subject_email=...)`인데, 이 두 인자는 `dependency_injector`의 "provided instance"
  체이닝(`pro_set_project.provided.get_config.call()['google_form_auto_reply']['...']`)으로
  `pro_set_project`가 만든 설정에서 뽑아낸다. `pro_google_form_auto_reply`는
  `providers.Singleton(GoogleFormAutoReply, ins_set_project=pro_set_project,
  ins_forms_client=pro_forms_client, ins_gmail_client=pro_gmail_client)`이다. `pro_cycle`은
  `providers.Singleton(Cycle, ins_procedure=pro_google_form_auto_reply)`인데
  — `src/app/procedure/cycle.py`의 `Cycle`은 작고 범용적인 드라이버로(`while True:
  ins_procedure.run_cycle(); time.sleep(ins_procedure.interval_sec)`), 예전에
  `GoogleFormAutoReply.run()`이 갖고 있던 루프를 대신 소유한다. `app`은
  `providers.Singleton(App, ins_cycle=pro_cycle)`이다.
  `bootstrap()`은 `Container()`를 만들고 `container.app()`을 반환한다(`Singleton` provider에
  접근하는 순간 실제로 인스턴스가 만들어진다 — 이 시점에 실제 서비스 계정 credential이
  필요하므로, credential이 없는 환경에서는 `bootstrap()`을 호출할 수 없다).
  **네이밍 주의사항**: 컨테이너 속성 이름을 `set_provider`처럼 `dependency_injector` 컨테이너
  내부와 충돌하는 이름으로 짓지 말 것 — 라이브러리 자체의 provider 등록 메커니즘을 조용히
  가려버려서, `Container()` 생성이 실제 원인과 무관해 보이는
  `TypeError: ...got multiple values for argument ...`로 깨진다.
  `src/app/app.py`의
  `App.run()`은 그냥 `self.ins_cycle.run()`을 호출한다. `LIVE.sh`는 이 서버의
  프로젝트 venv를 통해 `main.py`를 실행한다. 이 wiring에는 `dependency-injector` 패키지가
  필요하다(`requirements.txt`에 포함).
- **`src/app/procedure/once.py`**: 저자의 다른 프로젝트 템플릿에서 가져온 `Once` 클래스
  (`Cycle`과 비슷한 모양이지만 반복 없이 한 번만 도는 초기 설정용). `container.py`에
  wiring돼 있지 않고 이 기능에서 쓰이지도 않는다 — 실제로 살아있는 코드라고 가정하지 말 것.
- **`src/app/function/base.py`**: 저자의 다른 프로젝트들에서 가져온 범용 유틸리티 클래스들
  (`FileSystem`, `Memory`, `TimeKJW`, `ETC`). 자체 docstring에 따르면 이 파일은 다른
  프로젝트 로컬 모듈을 import하면 안 된다 — 리프(leaf)/유틸리티 모듈로 유지할 것.

## 테스트

`tests/`는 `_FormTarget`(`src/app/object/form_target.py`)의 CSV/mailed-email 상태 로드·저장,
도메인 리포트 집계, `__process_form_once`에서의 동일 이메일 dedup 판단,
`GoogleFormAutoReply`(`src/app/procedure/auto_reply_orchestrator.py`)의 3단계
재발송 판단 로직을 커버한다 — Forms/Gmail API 호출은 전혀 하지 않는다. 테스트는 로컬
파일만 필요로 하거나(`_FormTarget`), `__new__`로(실제 서비스 계정 credential이 필요한
`__init__`을 건너뛰고) `GoogleFormAutoReply`를 구성한 뒤 name-mangling된
`_GoogleFormAutoReply__send_mail`을 monkeypatch한다. 테스트 전용 의존성(운영용 Docker
이미지에는 포함되지 않음)을 설치하고 실행한다:
```bash
venv/bin/pip install -r requirements-dev.txt
venv/bin/python -m pytest tests/
```

## 실행 / 배포

```bash
venv/bin/python -m main          # 직접 실행
./LIVE.sh                        # 동일, 이 서버의 프로젝트 venv를 통해
docker build -t google-form-auto-reply .
docker run -d --name google_form_auto_reply --restart unless-stopped \
  -v $(pwd)/data:/app/data \
  -v $(pwd)/configs/thinking-volt-502003-b1-14ca6f480a1a.json:/app/configs/thinking-volt-502003-b1-14ca6f480a1a.json:ro \
  google-form-auto-reply
```

이 서버에서 사용자 계정은 `docker` 그룹에 속해 있어서 `docker` 명령에 `sudo`가 필요 없다
(`sudo docker ...`를 제안하지 말 것).

현재 이 서버에 `google_form_auto_reply` Docker 컨테이너로 배포돼 있다. **`docker restart`는
새로 빌드된 이미지를 반영하지 않는다** — 같은 태그로 재빌드해도 컨테이너는 생성될 때
사용했던 이미지 ID를 계속 실행한다. 코드가 바뀌면 이미지를 재빌드하고 컨테이너를 다시
만들어야 한다:
```bash
docker build -t google-form-auto-reply . && \
docker stop google_form_auto_reply && docker rm google_form_auto_reply && \
docker run -d --name google_form_auto_reply --restart unless-stopped \
  -v $(pwd)/data:/app/data \
  -v $(pwd)/configs/thinking-volt-502003-b1-14ca6f480a1a.json:/app/configs/thinking-volt-502003-b1-14ca6f480a1a.json:ro \
  google-form-auto-reply
```
`docker inspect --format '{{.Image}}' google_form_auto_reply`와
`docker inspect --format '{{.Id}}' google-form-auto-reply:latest`를 비교해서 새 이미지가
실제로 반영됐는지 확인할 것 — 두 값이 일치해야 한다.

## 도메인 메일 인증 (sumokhoe.co.kr)

발신 메일이 스팸함으로 들어가는 문제를 고치기 위해 SPF(`v=spf1 include:_spf.google.com ~all`)와
DMARC(`_dmarc` TXT, `p=none`)를 추가했다. DKIM은 이미 올바르게 설정돼 있었다. 전달성
(deliverability) 문제가 다시 생기면 우선 이 세 DNS 레코드부터 확인할 것.

## Git

이 프로젝트는 이제 git 저장소다. `.gitignore`는 `venv/`, `.idea/`, `configs/*.json`(서비스
계정 키 — 실제 비밀값, 절대 커밋하지 말 것), `.claude/settings.local.json`,
`data/*`(런타임 상태)를 제외한다 — 단 `data/mail_template/`는 메일 카피(`subject.txt`/
`body.txt`)를 담고 있어서 단순 런타임 상태가 아니라 소스로 취급돼 추적된다. 그 추적되는
폴더 안에서도 `data/mail_template/*/processed_response_id.csv`와
`data/mail_template/*/mailed_email.txt`는 둘 다 실제 응답자 이메일(PII)을 담고 있어서
소스 콘텐츠가 아니므로 별도로 다시 제외된다.
`data/mail_template/unique_email_domains.txt`(주기적인 이메일 도메인 리포트)도 재생성되는
결과물이지 소스 콘텐츠가 아니므로 마찬가지로 제외된다.
